# Deploying the Blue Balance API

Everything here is built and committed. What is left is the part that needs an
account in your name: signing up for a host, and pasting your own API keys.

The app cannot work until this is done — every authenticated screen calls the API
on mount, and App Review will reject a build they cannot sign into.

---

## What you need before starting

- A host account (Render, Railway, Fly — pick one below)
- An **OpenAI API key** if you want the AI coach to work. Without it,
  `POST /functions/ai-coach` returns 500 and the coach screen shows an error.
- Stripe keys **only** if you want billing on web/Android. iOS is free in 1.0, so
  you can skip these and ship.

You do **not** need to invent a signing key or paste a database connection
string. Both are handled for you.

---

## Option A — Render (fewest steps)

[`render.yaml`](../render.yaml) is a Blueprint: it declares the Postgres database
*and* the web service, and wires them together.

1. Push this repo to GitHub (already done).
2. In Render: **New → Blueprint → connect the repo.**
3. Render reads `render.yaml` and shows you what it will create: a
   `blue-balance-db` Postgres and a `blue-balance-api` web service.
4. It prompts for the keys marked `sync: false` — paste `OPENAI_API_KEY`, leave
   the Stripe ones blank if you are not billing yet.
5. Apply.

`DATABASE_URL` is filled in from the database Render creates. `AUTH_JWT_SECRET`
is generated by Render and stays stable across deploys. Migrations run at
startup, so there is no release command to set up.

When it finishes you get a URL like `https://blue-balance-api.onrender.com`.

**Free plan caveats, both worth knowing:** free instances sleep after inactivity,
so the first request after a sleep takes ~30 seconds — bad for an App Review
demo. Free Postgres also expires after 30 days. Move both to a paid tier before
submitting, or use a provider whose free tier does not sleep.

## Option B — Railway

Railway has no equivalent declarative file for provisioning a database, so this
is a few clicks:

1. **New Project → Deploy from GitHub repo.**
2. Set the service root directory to `server` so it finds the Dockerfile.
3. **New → Database → PostgreSQL.** Railway sets `DATABASE_URL` on the service
   automatically once they are in the same project.
4. In the service's Variables tab add:
   - `AUTH_JWT_SECRET` — generate with the command below
   - `NODE_ENV=production`
   - `OPENAI_API_KEY`
5. Generate a domain under Settings → Networking.

## Option C — Fly.io, or any host that runs a container

[`server/Dockerfile`](../server/Dockerfile) is a standard multi-stage build with
no host-specific assumptions. It listens on `$PORT` (default 8787), binds
`0.0.0.0`, and has a `/health` healthcheck.

```bash
docker build -t blue-balance-api ./server
docker run -p 8787:8787 \
  -e DATABASE_URL="postgres://..." \
  -e AUTH_JWT_SECRET="..." \
  -e NODE_ENV=production \
  blue-balance-api
```

Generate a signing key:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

## After it deploys — three checks

**1. It is alive.** Replace the host with yours:

```bash
curl https://your-api-host.com/health
```

Expect `{"status":"ok","database":"up"}`. If `database` says `down`, the
`DATABASE_URL` is wrong or the database is not reachable from the service.

**2. Auth works end to end:**

```bash
curl -X POST https://your-api-host.com/auth/signup \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"a-real-password"}'
```

Expect a JSON body containing `session.accessToken`.

**3. Point the app at it.** In the repo-root `.env`:

```
EXPO_PUBLIC_API_URL=https://your-api-host.com
```

Then rebuild. `EXPO_PUBLIC_*` is inlined **at bundle time**, so a build made
before this change still talks to `localhost` no matter what the file says now.

## Stripe webhook

Only if you are billing on web/Android. Add an endpoint in the Stripe dashboard
pointing at:

```
https://your-api-host.com/webhooks/stripe
```

Put its signing secret in `STRIPE_WEBHOOK_SECRET`. The route verifies the
signature and rejects anything older than five minutes, so a captured request
cannot be replayed.

## Before you call it production

- [ ] Paid tier for both the database and the service — free tiers sleep and expire
- [ ] `AUTH_JWT_SECRET` set (never rely on the generated dev key)
- [ ] `RESEND_API_KEY` and `EMAIL_FROM` set, so password reset can actually
      deliver. Without a provider the route returns 503 in production rather
      than stranding the user with a token it cannot send.
- [ ] Database backups enabled
- [ ] A demo account created on the deployed instance for App Review, with
      credentials you have personally verified by signing in
